# Documentation Site Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Publish an mdBook documentation site for claims-mcp on GitHub Pages, written for
evaluators first, with a page on how claims-mcp works alongside formal verification; slim the
README to a front door; register the docs' checkable statements as claims.

**Architecture:** Markdown sources in `docs/site/src/`, built by a pinned mdBook in a new
`docs.yml` workflow. Pull requests build and link-check (lychee, offline). Pushes to `main`
deploy to Pages. Detailed README sections move to the site, which becomes canonical.

**Tech Stack:** mdBook 0.5.4, lychee 0.24.2 via `lycheeverse/lychee-action`, GitHub Pages
actions, `just`, the claims MCP server.

**Spec:** `docs/superpowers/specs/2026-10-31-docs-site-design.md`

**Link rules for every page:** link between site pages with relative `.md` paths. Link to repo
files outside `docs/site/` (skill, SECURITY.md, specs, workflows) with absolute
`https://github.com/hypotheosis/claims-mcp/blob/main/...` URLs, because those files aren't in the
built site.

**Local link check** (not committed; CI uses lychee): run
`python3 -I <scratchpad>/linkcheck.py docs/site/book` after each build. The script walks the
built HTML, resolves every relative `href` to a file, and checks that every `#fragment` matches
an `id=` in the target. It prints each broken link and exits 1 if there are any.

### Task 2: Introduction and "Why claims-mcp"

**Files:** Write `introduction.md`. Create `why/problem.md`, `why/formal-verification.md` and
`why/limits.md`. Modify `SUMMARY.md`.

- [ ] **Step 1: `introduction.md`.** Start with the README's opening paragraph and bullets
  (README lines 1-19). Then a 30-second example in four short blocks, each a JSON tool call as
  an agent sends it:
  1. `add_claim` with statement "The server refuses writes after a hand edit of the catalog",
     kind requirement, integrity level 3, method `test`;
  2. `add_evidence` with a `file` anchor on the README integrity-seals paragraph and on the
     test that covers it, stance `supports`;
  3. `record_verdict` `supported` citing that evidence;
  4. the `claims-mcp recheck` output line after the anchored lines change (`changed`).
  Use the field names from the README's Anchors table. End with links to `why/problem.md`
  and `guides/install.md`. The install link is added to SUMMARY in Task 4, so it's only checked
  from then on.
- [ ] **Step 2: `why/problem.md`.** Three failure modes, one section each: documentation drifts
  from code, LLM output is accepted without checking, and the link from requirement to artifact
  is lost. For each, say how the ledger addresses it: atomic falsifiable claims, evidence the
  auditor gathered, append-only FEVER verdicts that must cite evidence, `derived_from` trace
  links, commit-pinned anchors and `recheck`, seals.
- [ ] **Step 3: `why/formal-verification.md`.** Follow the spec's section "2. Why
  claims-mcp" exactly:
  - what formal verification gives (Aeneas: Charon to LLBC to Lean; kernel-checked proof for
    every input);
  - the four gaps (spec, model, trusted base, coverage), each with what claims-mcp records for
    it;
  - the comparison table: question, scope, judge, drift, cost;
  - "Using them together" with concrete JSON for a `formal_proof` claim, the search anchor
    `{"search": {"pattern": "\\bsorry\\b|\\badmit\\b|^axiom ", "scope": ["proofs"]}}` with zero
    hits, differential-testing evidence, and a spec-fidelity claim reviewed by someone other
    than the spec's author;
  - de Moura's four vetting questions, mapped to claims in a table;
  - the paragraph on LLMs writing Lean;
  - a "Sources" list: https://github.com/AeneasVerif/aeneas, https://lean-lang.org,
    https://thedataexchange.media/leo-de-moura-lean-aws/.

  No private hostnames, people or systems.
- [ ] **Step 4: `why/limits.md`.** A verdict is judgment backed by cited evidence, not proof.
  The server records and never runs your code (except `git grep`/`rev-parse` for anchors). The
  ledger is only as good as its evidence. Seals deter casual edits but are not cryptographic
  security, because the HMAC key is in the public source (README lines 172-174). Anchors need
  git.

### Task 6: docs.yml workflow

**Files:** Create `.github/workflows/docs.yml`.

- [ ] **Step 1: Write the workflow**

```yaml
# Documentation site: builds the mdBook in docs/site and checks its links on pull requests;
# on pushes to main, also deploys it to GitHub Pages.
name: Docs

on:
  pull_request:
    paths: ["docs/site/**", ".github/workflows/docs.yml"]
  push:
    branches: [main]
    paths: ["docs/site/**", ".github/workflows/docs.yml"]
  workflow_dispatch:

permissions:
  contents: read

concurrency:
  group: docs-${{ github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}

env:
  MDBOOK_VERSION: v0.5.4
  MDBOOK_SHA256: 5222beabd3e37dc5be0d18ff99b79058469354db5c220153a1b92db5ba12be89

jobs:
  build:
    name: build and link-check
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - name: Install mdBook
        run: |
          archive="mdbook-${MDBOOK_VERSION}-x86_64-unknown-linux-musl.tar.gz"
          curl -sSfL -o "$archive" \
            "https://github.com/rust-lang/mdBook/releases/download/${MDBOOK_VERSION}/${archive}"
          echo "${MDBOOK_SHA256}  ${archive}" | sha256sum -c -
          mkdir -p "$HOME/.local/bin"
          tar -xzf "$archive" -C "$HOME/.local/bin" mdbook
          echo "$HOME/.local/bin" >> "$GITHUB_PATH"
      - name: Build
        run: mdbook build docs/site
      - name: Check links (internal, offline)
        uses: lycheeverse/lychee-action@e7477775783ea5526144ba13e8db5eec57747ce8 # v2.9.0
        with:
          args: >-
            --offline --include-fragments --no-progress
            --root-dir ${{ github.workspace }}/docs/site/book
            docs/site/book
          fail: true
      - uses: actions/configure-pages@45bfe0192ca1faeb007ade9deae92b16b8254a0d # v6.0.0
        if: github.event_name != 'pull_request'
      - uses: actions/upload-pages-artifact@fc324d3547104276b827a68afc52ff2a11cc49c9 # v5.0.0
        if: github.event_name != 'pull_request'
        with:
          path: docs/site/book

  deploy:
    name: deploy to Pages
    if: github.event_name != 'pull_request'
    needs: build
    runs-on: ubuntu-latest
    permissions:
      pages: write
      id-token: write
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - id: deployment
        uses: actions/deploy-pages@368f82528645a54fb793d4d04e342629a3f51346 # v5.0.1
```

`configure-pages` needs Pages enabled. Pull requests skip it, so PR builds pass before the
owner enables Pages.

- [ ] **Step 2: Validate the YAML.** Run
