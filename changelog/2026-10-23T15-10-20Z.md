# claims-mcp 0.1.0: PR #10 review fixes for integrity seals

## Fixed
- **Lowering `schema_version` to 1 no longer launders edits.** Previously, `seal --adopt` on a
  "v1" catalog dropped every seal and re-adopted everything, so a hand edit plus changing
  `"schema_version": 2` to `1` produced a catalog that verified.
  - A genuine v1 file has no seals. `verify` now reports `schema_version` ("lowered by hand")
    when a v1 catalog carries any seal, and the store returns `CatalogTampered` instead of
    `UnsealedCatalog`.
  - `seal --adopt` refuses such a catalog with `AdoptRefused` and changes nothing.
- **Deleting the newest claim is no longer laundered.** The single header seal is replaced by
  one seal per counter (`next_claim_seq_seal` and `next_evidence_seq_seal`, each binding
  `schema_version` and its value). `seal --adopt` no longer has a header exception, so it
  never re-seals a present-but-wrong seal. Deleting the last claim and decrementing
  `next_claim_seq` breaks that counter's seal and is refused like any other edit.
- **The merge case that needed the header exception now needs nothing.** Each counter has its
  own seal, placed next to it. When one branch added a claim and another added evidence, git
  merges them cleanly and every seal still verifies. This was checked with a real
  `git merge-file` on catalogs written by the release binary.

## Tests
- New: the `schema_version` downgrade (seal module and store), deleting the newest claim
  while lowering `next_claim_seq`, and an adopted record relabeled as `server`.
- The counter test is renamed to `next_evidence_seq`. The v1 fixtures now strip every seal,
  as a genuine v1 file would.
- 83 tests in total.

## Catalog
- Re-ran `seal --adopt` on `claims.json`. The old header seal was dropped, and the two
  counters were adopted. All other seals were unchanged, and the catalog verifies with 125
  records.
