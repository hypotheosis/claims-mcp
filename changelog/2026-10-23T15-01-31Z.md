# claims-mcp 0.1.0: integrity seals on the catalog (issue #9)

## Added
- `src/seal.rs`: an HMAC-SHA256 seal, under a key built into the binary, on the catalog header
  and on every claim, evidence item, and verdict. Each MAC covers the record and its place in
  the catalog:
  - evidence binds its claim id
  - a verdict binds its claim id, its index, and the previous verdict's MAC (a chain)
  - a claim binds its own fields, its evidence ids, and its latest verdict's MAC
  - the header binds `schema_version` and both id counters

  A gap below `next_claim_seq` reveals a deleted claim. MACs are computed over a
  `serde_json::Value` (sorted keys), so reformatting or reordering keys does not break them.
- **Strict, always-on verification.** Every write verifies every seal first. On any failure,
  the server refuses the write with `CatalogTampered`, whose message lists the failing records
  and tells the operator or LLM to restore from git and redo the change through the tools. A
  schema v1 catalog gets `UnsealedCatalog`, which says a maintainer must run `seal --adopt`.
  Both are logged with `tracing::error!`. There is deliberately no flag or environment variable
  to relax this. Reads and `audit_report` keep working.
- After each successful tool write, `seal::reseal` re-seals as `server` only the records whose
  seal no longer matches. Untouched records keep their seal, including the `adopt` origin.
- CLI subcommands, none of them MCP tools:
  - `claims-mcp verify [--json]` exits 1 on any failure.
  - `claims-mcp seal --adopt` seals unsealed records as `adopt`. It refuses (`AdoptRefused`)
    when any record has a present-but-wrong seal or a claim is missing. The catalog header is
    the only exception: after a merge conflict on the counters, it is re-sealed once every
    other record verifies.
- `audit_report` gains an `integrity` section (`verified`, `records`, `problems`, `adopted`).
- The Typst report takes the output of `verify --json` as an `integrity` input. It shows the
  status on the cover, a warning on the result when the check failed, and a new Integrity
  section. `just report` produces that input first. The parity test passes it, so the template
  metadata still equals `audit_report`.
- CI runs `claims-mcp verify` in the check job. The report job installs Rust for `just report`.
- New dependencies: `hmac` 0.13 and `sha2` 0.11 (MSRV 1.89 still builds).

## Changed
- `schema_version` is now 2. Version 1 is still read, but it never verifies, so it is
  read-only until `seal --adopt` migrates it.
- The repository's `claims.json` was migrated with `seal --adopt` (120 records). CLM-0005
  (which said "schema_version 1") was then retired through the MCP tools and replaced by
  CLM-0037, with new evidence (EVD-0045, EVD-0046) and a verdict. Its five children now derive
  from CLM-0037.
- README: "hand edits are safe" became an "Integrity seals" section covering the threat model,
  recovery, `verify`, `seal --adopt`, merge behavior, and Claude Code deny rules. Also updated:
  the subcommand table, the report inputs, and the CI list.
- Design spec sections 3.1 and 5.1, and the `claims-audit` skill: never edit `claims.json`
  directly; on a tampering error, stop, tell the user, and restore from git; never run
  `seal --adopt`. The server's MCP instructions say the same.

## Diverged from the issue
- The issue suggested an RFC 8785 (JCS) crate for canonical bytes. Serializing a
  `serde_json::Value`, whose objects are sorted `BTreeMap`s, gives the same independence from
  key order and whitespace with no extra dependency.
- The issue's `sealed_by: "adopt"` became `seal: {"by": "adopt" | "server", "mac": ...}`. The
  origin is covered by the MAC.
- The issue proposed an id-gap check for evidence too. The claim seal already covers its
  evidence ids, so only claim ids are gap-checked.
- Unmigrated v1 catalogs get a dedicated `UnsealedCatalog` error instead of `CatalogTampered`,
  because "restore from git" is the wrong advice for a catalog that was never sealed.
