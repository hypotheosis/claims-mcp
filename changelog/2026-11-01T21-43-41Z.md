# Mechanical releases: release-prepare, release-ship, release-abort (issue #37)

- Releases are cut by `just release-prepare <level>` and `just release-ship`, and abandoned by
  `just release-abort`, modeled on bolt_deployment_controller's flow. Nothing in a release is
  written by hand. `release.toml` configures cargo-release: one local commit
  `chore: Release vX.Y.Z` that bumps `Cargo.toml`, `Cargo.lock` and
  `report/audit-notes.toml` and adds the changelog entry, plus an annotated tag; nothing is
  pushed or published to crates.io.
- `release-ship` differs from bolt's in two ways. It waits for the review bot's review and stops
  on any unresolved review thread, because main's ruleset requires threads to be resolved. And it
  has no tag-only path: the release is always a single-parent commit directly on `origin/main`,
  landed through a pull request with a merge commit, and the tag is moved to that merge commit
  locally before it is pushed, since the "Protect release tags" ruleset makes pushed tags
  immutable.
- `scripts/release-notes.sh <from> <to>` builds the notes from the first-parent merge commits in
  the range, grouped by the conventional-commit type of each pull request's title, each linked to
  its pull request, leaving out the `chore: Release` pull request. The pre-release hook
  (`scripts/release-changelog.sh`) writes them as the changelog entry, and `release.yml`'s
  publish step passes them as `--notes-file` instead of `--generate-notes`, so the entry and the
  GitHub release body are the same bytes. The links use a fixed repository URL rather than
  `GITHUB_REPOSITORY`, so local and CI output cannot differ.
- `report/audit-notes.toml` no longer gets a paragraph per version. The assessment keeps the
  0.1.0 audit's paragraph and one fixed paragraph on what was audited as claims since. The issue
  proposed "Changes from 0.2.5 on are audited as claims in their pull requests"; it is worded as
  "Since 0.2.5" with the 0.2.0 to 0.2.5 exceptions named, because two of 0.2.5's own pull
  requests (#30, #33) were not audited, and dependency updates are not.
- CI: a `release scripts` job runs `shellcheck` and `just release-test` with cargo-release
  installed, and a `release branch matches Cargo.toml` job fails a `release/v*` pull request
  whose branch does not name its version (`scripts/release-branch-check.sh`).
- `scripts/release-test.sh` covers the notes' grouping and ranges, every refusal in prepare, ship
  and abort, tagging the merge commit, main moving mid-ship, failing or missing checks, a
  missing review, unresolved review threads, and an end-to-end prepare and ship with the real
  cargo-release whose changelog entry and release notes are compared byte for byte.
- "Releasing" in `docs/site/src/development.md` describes the three commands and what each
  refuses.
