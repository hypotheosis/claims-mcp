# `claims-mcp rebase`: replay a branch's ledger records onto main's (issue #32)

- New subcommand `claims-mcp --catalog claims.json rebase --onto MAIN --base BASE [--json]`.
  It takes three ledgers: the branch's own (`--catalog`), the other side's (`--onto`, usually
  main's), and the branch's at the merge base (`--base`, missing file = empty ledger). It
  rewrites `--catalog` as `--onto` plus everything the branch added since `--base`, and prints
  the old-to-new id of every claim and evidence item the branch added.
- Replayed: new claims (next free ids, original order), new evidence on new or existing claims
  (next free ids, id order), verdicts appended to existing claims (after the other side's), and
  `update_claim`/`retire_claim` field changes to existing claims. `derived_from` links and the
  evidence ids that verdicts cite are rewritten. The result is resealed; `--catalog` is locked,
  verified first, and replaced atomically like any write. `--onto` and `--base` are only read,
  through the new lockless `store::load_file`, so no lock file is left beside them.
- Why `--base` is required: colliding records have equal ids on both sides, so without the
  merge base there is no reliable way to tell which records the branch added.
- Refusals (nothing written, exit 1): an input fails its integrity check (so a hand edit can't
  be laundered); an input does not descend from `--base` (counters below `--base`'s, or a
  claim's evidence or verdicts not starting with `--base`'s); `--onto` already holds the
  branch's new records unchanged (a second run, which would otherwise duplicate them); both
  sides changed a claim's fields differently; the branch added records to a claim `--onto`
  retired; links from both sides form a `derived_from` cycle.
- When `--onto` equals `--base`, the result is identical to the branch's ledger, ids and seals
  included.
- Code: `src/rebase.rs` (pure function `rebase(base, branch, onto)`), `ClaimsError::Rebase`,
  and `Catalog::{next_evidence_seq, claim_mut, append_replayed_claim, advance_evidence_seq}`;
  `Catalog::reaches` and the test helper `child_of` are now `pub(crate)`. `OwnFields`
  destructures `Claim` without `..`, so a new claim field fails to compile until the rebase
  decides how to merge it.
- Docs: new guide `docs/site/src/guides/parallel-branches.md` with the merge procedure (rebase
  inside `git merge --no-commit`, so there is no second textual conflict); CLI reference row;
  CI guide and seals page point to it; the claims-audit skill's "When main's ledger moved" uses
  `rebase` when the installed binary has it and keeps "record again" as the fallback.
- Tested end to end with real git branches and the release binary: the issue's reproduction
  (clean textual merge, duplicate `EVD-0001`) and a conflicting case with new claims on both
  sides both end in a ledger that passes `verify`.
- Not done: option 1 of the issue (ids that cannot collide). Detection in CI (option 3) stays.
